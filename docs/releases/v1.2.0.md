# JellyNews v1.2.0 — Notes de release

Date : 2026-11-11

## Résumé

JellyNews v1.2.0 corrige les principales causes de classement en spam observées chez certains fournisseurs (alors que le même compte SMTP passait depuis d’autres outils), et fiabilise l’envoi des campagnes longues.

## Délivrabilité

- **En-têtes `Date` et `Message-ID`** : ni `EmailMessage` ni `smtplib.send_message` ne les ajoutent ; leur absence est pénalisée par les filtres anti-spam. `Message-ID` utilise le domaine de l’adresse d’expéditeur.
- **Vraie version texte** : la partie `text/plain` n’est plus une phrase générique mais reprend le contenu de la newsletter (titre, période, introduction, sections, titres, synopsis, liens, lien de désinscription). Elle respecte le bloc « Introduction » désactivé et filtre les liens non publics comme le HTML. Elle est encodée en quoted-printable (et non en base64, que les émojis faisaient choisir).
- **Nom d’expéditeur** : nouveau champ optionnel « Nom affiché » dans l’onglet SMTP (`smtp_sender_name`). Le From devient `Nom <adresse>`. Sans nom, il reste l’adresse seule, comme avant ; un ancien `smtp_sender` déjà au format `Nom <adresse>` est respecté.
- **Poids de l’email** : au plus 15 affiches incorporées (contre 50). Le mode par défaut (`embed`) est inchangé.

## Robustesse de l’envoi

- Une connexion SMTP est ouverte à chaque vague : un serveur qui coupe pendant la pause entre vagues n’interrompt plus le reste de la campagne.
- En cas de `SMTPServerDisconnected` en cours de vague, JellyNews se reconnecte et retente une seule fois le destinataire concerné.
- Si la reconnexion échoue sur une vague suivante, seuls les destinataires de cette vague sont comptés en échec. Un échec de la toute première connexion remonte comme avant.
- Téléchargement des affiches : les refus d’accès Jellyfin (401/403) sont journalisés en erreur avec une piste de correction (clé API, droits sur les bibliothèques), distincts des autres erreurs HTTP et réseau.

## Confidentialité

- Les échecs d’envoi journalisent désormais le diagnostic SMTP neutralisé au lieu de la trace brute : la trace d’un `SMTPRecipientsRefused` contenait l’adresse du destinataire en clair.

## CI et dépôt

- Tests exécutés avant tout build d’image, sur GitHub comme sur Gitea (Python 3.12, comme l’image).
- Workflow Gitea générique : le registre est fourni par la variable Actions `REGISTRY` (obligatoire), l’identifiant par `REGISTRY_USER` (propriétaire du dépôt par défaut), le jeton par le secret `REGISTRY_TOKEN`. Tag de version publié sur les tags `v*`, `latest` réservé à `main`.
- `requirements-dev.txt` (pytest), `.dockerignore` complété, démarrage FastAPI migré vers `lifespan`.

## Compatibilité

- Aucune migration de base : `smtp_sender_name` vaut une chaîne vide par défaut ; les anciennes sauvegardes s’importent sans changement.
- Désinscription one-click RFC 8058, masquage des adresses et import/export des réglages inchangés.

## Points d’attention

- **Plus de 15 nouveautés en mode `embed`** : les affiches au-delà de la 15ᵉ pointent vers `jellyfin_external_url` (ou `jellyfin_url`). Si Jellyfin n’est pas joignable depuis Internet, elles apparaîtront cassées chez les abonnés.
- SPF, DKIM et DMARC restent indispensables et se configurent côté DNS et fournisseur SMTP.

## Validation conseillée

1. Renseigner le nom d’expéditeur et `app_public_url`.
2. Sur une instance de test dont le seul abonné est une adresse mail-tester.com fraîche, lancer « Envoyer maintenant ».
3. Vérifier dans le rapport : présence de `Date`/`Message-ID`, From avec nom, partie texte cohérente avec le HTML, `List-Unsubscribe`.
4. Le bouton « Newsletter test » n’envoie ni `List-Unsubscribe` ni affiches incorporées : il ne reflète pas une campagne réelle.

## Rollback

Avant mise à jour, sauvegarder le volume `data/`. En cas de rollback vers v1.1.3 :

1. arrêter JellyNews v1.2.0 ;
2. relancer l’image v1.1.3 (la clé `smtp_sender_name` reste en base et est simplement ignorée) ;
3. purger le cache navigateur/proxy si les assets versionnés `?v=1.2.0` ont déjà été servis.
